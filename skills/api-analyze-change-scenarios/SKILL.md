# 改动分析与场景设计

读 `00-context.md`，产出 `01-change-analysis.md` 和各批次的 `docs/batch<N>/02-scenarios.md`。
产物结构见 [TEMPLATES.md](TEMPLATES.md)，红线见 `../api-generate-api-tests/CONVENTIONS.md`。

这一步的质量决定后面所有环节的质量，宁可多问几个问题，也不要带着猜测往下走。

**批次贯穿全程**：批次在第二步就定下来，此后行为差异分析、场景设计、mock、造数、
用例、执行全部按同一套批次逐批推进——每次只讲透一个批次的改动逻辑和测试内容，
用户跟着一批一批走完整条流水线，逐步吃透这次改动；不要先把全部改动点的行为差异
一次性啃完，再机械地只在场景设计环节分批。

## 第零步：校验必填输入

开跑前先核对 `00-context.md` 的必填项，全部通过后再进入第一步。任何一项失败都停下来问用户，
不许边猜边跑：

| 项           | 校验方式                                                           | 失败处理                        |
| ----------- | -------------------------------------------------------------- | --------------------------- |
| 代码仓库本地路径    | 路径存在、是 git 仓库（`git -C <path> rev-parse --is-inside-work-tree`） | 让用户重填或先 clone               |
| base 分支     | `git -C <path> rev-parse <base>` 能解出 commit                    | 让用户确认分支名 / 是否需要 `git fetch` |
| feature 分支  | `git -C <path> rev-parse <feature>` 能解出 commit                 | 同上                          |
| Pod IP      | 非空、形如 IPv4                                                     | 让用户提供正确 IP                  |
| operation 名 | 非空                                                             | 让用户补                        |
| 产物目录        | 存在或可创建                                                         | 让用户确认                       |

校验通过后在对话里一句话确认「必填项齐全」，再往下走。占位符（`xxx`、`TBD`、`?`、空串）
一律视为缺失，不接受。`appid` 不是必填，用户没给不要拦。

## 第一步：圈定改动面

1. `git diff <base>...<feature>` 拿到改动清单（文件、类、方法、改动性质）。
  diff 很大时先看 `--stat` 再逐个文件看。
2. 用 operation 名在代码里定位入口实现：搜 contract 接口定义、`*ServiceImpl`、注解声明的路径。
  必须定位到**具体文件路径和方法名**。定位不到就停下来问用户。
3. 判断每个改动点是否落在该 operation 的调用链上。不在链上的单独列出来告诉用户
  "本次接口测不到这些改动"，由用户决定是否补充别的接口。

这一步只产出**改动清单**（编号、文件、类#方法、改动性质、是否在调用链上），不展开
"改前/改后行为"——具体行为差异留到第三步按批次再讲，避免在还没分批之前就把全部
改动点的细节啃一遍。

## 第二步：规划批次

只凭改动清单本身的性质（哪个改动点是主流程/最基础能力、哪些改动点共享同一个类
或字段、影响面有多大）划分批次，先不深入行为差异细节：

- **batch1 固定收纳 1–3 个改动点**：挑能代表本次改动最核心/最基础能力的改动点，
  跑通它们才证明链路整体打通了。
- **剩余改动点默认全部塞进 batch2**，不硬拆。
- 改动点数量本身就很多（预判会引出大量候选场景），或者某个改动点明显是"多分支
  组合"型（比如新增一组开关矩阵），在这一步就先按业务模块或改动性质切出更多批次；
  批次骨架经用户确认后，如果某批次做到第三步发现候选场景数远超 30 条，允许当场
  再拆出一个新批次，如实告诉用户原因，不用假装最初就规划对了。
- 有紧耦合的改动点（共享同一个类/字段/开关，改一个必须连带看另一个）必须同批。
- 同一批内尽量共享同一套前置条件（同一组 mock、同一份配置），减少批内切换成本。
- 用户明确要求不分批时，全部改动点归 batch1，第三步不再逐批展开，一次写完。

产出：给改动清单加一列「批次」，加一节**批次安排**（每批涵盖哪些改动点编号、大致
覆盖重点——这时候还没有行为差异细节，覆盖重点只能写"XX 相关的核心变化"这类粗
粒度描述），写入 `01-change-analysis.md`，状态头**批次进度**行标「骨架待确认」
（写法见 CONVENTIONS.md「md 状态头」）→ **暂停**，请用户确认批次划分本身是否
合理。这一步用户凭对改动范围的直觉判断就够了，不需要先读懂每个改动点的具体行为。

## 第三步：逐批分析与设计场景

批次骨架确认后，从 batch1 开始，每次只完整走完**当前一个批次**的分析和场景设计，
包含以下三件事：

### 1. 读懂本批改动点的行为差异

对本批每个改动点写清楚三件事：**改前行为、改后行为、进入这段代码的条件**。
这三件事必须是人话，类名只作为「依据」角标（红线见 CONVENTIONS.md「结论区禁止用
代码标识符做主语」，共享改动/影响面广的写法参考 TEMPLATES.md 的 C3 示例）。

同时扒出本批改动点这条调用链的依赖，分类登记（这是下游两个造数 skill 的输入）：

- 调用的外部 HTTP / RPC 接口（接口名、入参、返回结构）
- 读写的 DB 表（库名、表名、字段）
- 读写的 Redis key（集群名、key 格式、TTL）
- 读取的配置中心 key（文件名、key、用途）
- 收发的消息中间件 topic（subject、消息结构）

这一步可以自由做只读探查：APM 工具捞真实 trace 看报文长什么样、数据库查询 MCP 查表结构、
配置中心查询 MCP 读当前值、真实调一次接口看返回。

有 PRD 就用 PRD 校正理解（PRD 用文档读取工具读）。**PRD 与代码不一致时，
把差异点单独列一节问用户以哪边为准，不要自己裁决。** 没有 PRD 时纯代码推导，
把推导出的预期行为单列一节请用户确认。

### 2. 设计本批场景

场景从本批改动点的逻辑分支里长出来：if/else 两侧、switch 各分支、异常路径、
配置开关的开与关、边界值、空值。

每个场景必须写明**它对应哪个改动点**，另加一句**"为什么设这条"**——写清这条场景
想验证改动点的哪个具体行为。这两条是硬要求：没有对应改动点的场景不要写；写不出
"为什么"说明自己也没想清楚，删掉或者回去重想。

允许额外提议**少量**基础回归场景（确认改动点周边没被搞坏），标记为
"非改动点，建议但可删"，由用户决定去留。

### 3. 穷举本批每个场景的预期产出

每个场景必须列一张**预期产出表**，把调用链跑完后每一步的关键字段写清楚，不要
只写"成功/失败"或"走 X 分支"。这张表是给下游 `api-write-pytest-cases` 生成断言用
的规格明细，不是给用户逐行审的内容——用户 review 时只需要看「覆盖检查」那张
总表，确认场景覆盖到位、逻辑合理即可，除非想抽查某个具体字段才需要点进某条场景
看这张表。表结构固定四列：

| 阶段 / 处理器 | 关键产出字段 | 期望值 | 值的来源 | 是否随机 |
| -------- | ------ | --- | ---- | ---- |

四列的填法：

- **阶段 / 处理器**：调用链上的一个节点（网关、准入、路由、召回、渲染、投递……
  按被测接口的实际链路命名）。
- **关键产出字段**：这一步对下游或最终响应有影响的字段。响应字段用 jsonpath 写
  （`$.data.orderId`），中间产物写字段名 + 出处（`ctx.candidate.prdType`）。
- **期望值**：具体值或明确的匹配规则（等值、包含、正则、非空、集合成员）。
- **值的来源**：这个值**来自哪里**——代码常量 / 入参回显 / DB 查询 / Redis / mock 报文 /
  配置中心 / 用户提供 / 外部真实接口。**必须写清楚**，写不出就是存疑点。
- **是否随机**：同入参多次运行输出是否稳定。填"是"就只允许存在性 / 结构断言，
  下游 skill 会照此写用例。

判断"是否漏字段"的口径：**如果这个字段错了或缺了，能不能证明命中了目标分支**。
能证明的就必须列。模板 ID、券面值、路由目标、拼装出的 URL、消息 payload 里的关键 key
都属于这类，不许省。

**关于"值的来源"**：环境相关的业务常量（模板 ID、任务 ID、券值、可用 cid、库存 ID
等）只存在于目标环境，不许从仓库 SQL、mock 平台历史值、PRD 示例值抄。
拿不到就查环境或问用户，进存疑点。

### 汇总与暂停

把本批的行为差异、依赖清单、PRD 对照追加进 `01-change-analysis.md` 的四/五/六节，
并把 `01` 状态头的**批次进度**行更新为「batch\<N\> 待确认」。

本批场景单独写成 `docs/batch<N>/02-scenarios.md`，只含本批场景（总览、覆盖检查、
场景详情、存疑点），状态头阶段写成 `batch<N>/02-测试场景`。不要再写一份汇总所有
批次的 `docs/02-scenarios.md`，也不要在本批文件里给其他批次留占位行。批次安排
已经在 `01` 里，本批场景文件不必再抄一份。

→ **暂停**，请用户一次性确认本批的改动逻辑和场景设计。

用户确认（或直接改 md）后，把本批 `02-scenarios.md` 的状态改成 `已确认`，并把
`01` 的批次进度改成「batch\<N\> 已确认」，随后交给主编排走本批次的阶段 3-6
（mock、造数、用例、执行）；本批阶段 6 完成、收尾汇报后，再回到本步骤做下一批次。
全部批次的场景都确认后，`01-change-analysis.md` 的整体状态才能改成 `已确认`。

### 批次交付红线

每次只完整讲透当前这一批的行为差异和场景，不提前碰下一批的内容——即使觉得
"反正代码都看过了""这次改动不大一次讲完更省事""这批和下一批逻辑连着不如一起讲"，
也不例外。**"用户想尽快看到完整方案"不等于"要一次看完所有批次的分析和场景"**——
除非用户明确说"不分批"或明确要求把所有批次一次讲完，否则默认按批次逐一推进。

| 想法 | 现实 |
| --- | --- |
| 反正代码都翻过了，顺手把所有改动点的行为差异都写了吧 | 看代码和讲清楚是两回事；一次抛给用户所有批次的行为差异，等于又把"分批消化"的初衷丢了 |
| 这次改动不大，一次讲完更省事 | 改动大小不是分批的理由；哪怕总共只有几个改动点，一次全灌给用户还是会看漏、来不及提问 |
| 这批和下一批的改动点逻辑上有关联，不如一起讲清楚 | 有关联就把它们分进同一批（第二步的规则），而不是分了批又在执行时把批次边界当摆设 |

出现以下任一情况，停下来只保留当前批次的产出：

- 已经在写下一批改动点的行为差异或场景，但当前批次还没被用户确认；
- 因为"怕多轮来回麻烦"而想把没确认的批次也顺手讲了；
- 用户没有明说"不分批"或"一次讲完"，只是笼统地要一份"完整方案"。

## 收尾

两份 md 都要有存疑点章节。把存疑点逐个问用户，答案回填正文。
存疑点清空前不要把状态改成 `已确认`。
