# 改动分析与场景设计

读 `00-context.md`，产出 `01-change-analysis.md` 和 `02-scenarios.md`。
产物结构见 [TEMPLATES.md](TEMPLATES.md)，红线见 `../api-generate-api-tests/CONVENTIONS.md`。

这一步的质量决定后面所有环节的质量，宁可多问几个问题，也不要带着猜测往下走。

## 第零步：校验必填输入

开跑前先核对 `00-context.md` 的必填项，全部通过后再进入第一步。任何一项失败都停下来问用户，
不许边猜边跑：


| 项           | 校验方式                                                           | 失败处理                        |
| ----------- | -------------------------------------------------------------- | --------------------------- |
| 代码仓库本地路径    | 路径存在、是 git 仓库（`git -C <path> rev-parse --is-inside-work-tree`） | 让用户重填或先 clone               |
| base 分支     | `git -C <path> rev-parse <base>` 能解出 commit                    | 让用户确认分支名 / 是否需要 `git fetch` |
| feature 分支  | `git -C <path> rev-parse <feature>` 能解出 commit                 | 同上                          |
| Pod IP      | 非空、形如 IPv4                                                     | 让用户提供正确 IP                  |
| operation 名 | 非空                                                             | 让用户补                        |
| 产物目录        | 存在或可创建                                                         | 让用户确认                       |


校验通过后在对话里一句话确认「必填项齐全」，再往下走。占位符（`xxx`、`TBD`、`?`、空串）
一律视为缺失，不接受。`appid` 不是必填，用户没给不要拦。

## 第一步：圈定改动面

1. `git diff <base>...<feature>` 拿到改动清单（文件、类、方法、改动性质）。
  diff 很大时先看 `--stat` 再逐个文件看。
2. 用 operation 名在代码里定位入口实现：搜 contract 接口定义、`*ServiceImpl`、注解声明的路径。
  必须定位到**具体文件路径和方法名**。定位不到就停下来问用户。
3. 判断每个改动点是否落在该 operation 的调用链上。不在链上的单独列出来告诉用户
  "本次接口测不到这些改动"，由用户决定是否补充别的接口。

## 第二步：读懂行为差异

对每个在调用链上的改动点，写清楚三件事：**改前行为、改后行为、进入这段代码的条件**。
这三件事必须是人话，类名只作为「依据」角标（红线见 CONVENTIONS.md「结论区禁止用
代码标识符做主语」，共享改动/影响面广的写法参考 TEMPLATES.md 的 C3 示例）。

同时扒出这条调用链的全部依赖，分类登记（这是下游两个造数 skill 的输入）：

- 调用的外部 HTTP / RPC 接口（接口名、入参、返回结构）
- 读写的 DB 表（库名、表名、字段）
- 读写的 Redis key（集群名、key 格式、TTL）
- 读取的配置中心 key（文件名、key、用途）
- 收发的消息中间件 topic（subject、消息结构）

这一步可以自由做只读探查：APM 工具捞真实 trace 看报文长什么样、数据库查询 MCP 查表结构、
配置中心查询 MCP 读当前值、真实调一次接口看返回。

有 PRD 就用 PRD 校正理解（PRD 用文档读取工具读）。**PRD 与代码不一致时，
把差异点单独列一节问用户以哪边为准，不要自己裁决。** 没有 PRD 时纯代码推导，
把推导出的预期行为单列一节请用户确认。

## 第三步：规划批次骨架

先不写场景细节，只从每个改动点的逻辑分支里数出全部候选场景点：if/else 两侧、
switch 各分支、异常路径、配置开关的开与关、边界值、空值。每条候选场景先只定
**标题**和**对应改动点**，不展开预期产出。

允许额外提议**少量**基础回归场景（确认改动点周边没被搞坏），标记为
"非改动点，建议但可删"，同样只定标题。

数完候选场景后分批：

**batch1 固定是主流程（冒烟）**：挑核心成功路径的 1–5 条候选场景，跑通它才证明链路是通的。
**剩余候选场景默认全部塞进 batch2**，不硬拆。**只有 batch2 超过 30 条**时才继续切成
batch3、batch4，按负向、边界、回归的顺序排。

规则：

- batch1 只放主流程，不掺负向/边界；
- 剩余场景合并进 batch2，不要为了分批而分批；
- 单批超过 30 个场景（按场景条数算，不按 parametrize 展开后算）才继续拆下一批；
- 有依赖关系的场景（B 的预期依赖 A 的结论）必须同批，或者 A 在更前的批次；
- 同一批内尽量共享同一套前置条件（同一组 mock、同一份配置），减少批内切换成本；
- 用户明确要求不分批时，全部候选场景归 batch1，第四步不再逐批展开，一次写完。

产出仅含标题级信息的**场景总览表**（场景 ID、标题、对应改动点、类型、优先级、批次）
和一节**批次安排**（每批场景数、覆盖重点），写入 `02-scenarios.md`，状态头的
**批次进度**行标「骨架待确认」（写法见 CONVENTIONS.md「md 状态头」）→ **暂停**，
请用户确认批次边界和场景范围是否合理——这一步只 review 骨架，不涉及预期产出细节。

## 第四步：逐批设计场景

批次骨架确认后，从 batch1 开始，每次只完整展开**当前一个批次**的场景，
展开内容包含以下两件事：

1. **场景本身**：写明**它对应哪个改动点**，另加一句**"为什么设这条"**——写清这条
   场景想验证改动点的哪个具体行为。这两条是硬要求：写不出"为什么"说明自己也没想
   清楚，删掉或者回去重想。
2. **预期产出表**：把调用链跑完后每一步的关键字段写清楚，不要只写"成功/失败"或
   "走 X 分支"。这张表是给下游 `api-write-pytest-cases` 生成断言用的规格明细，不是给
   用户逐行审的内容——用户 review 时只需要看「覆盖检查」那张总表，确认场景覆盖到位、
   逻辑合理即可，除非想抽查某个具体字段才需要点进某条场景看这张表。表结构固定四列：

   | 阶段 / 处理器 | 关键产出字段 | 期望值 | 值的来源 | 是否随机 |
   | -------- | ------ | --- | ---- | ---- |

   四列的填法：

   - **阶段 / 处理器**：调用链上的一个节点（网关、准入、路由、召回、渲染、投递……
     按被测接口的实际链路命名）。
   - **关键产出字段**：这一步对下游或最终响应有影响的字段。响应字段用 jsonpath 写
     （`$.data.orderId`），中间产物写字段名 + 出处（`ctx.candidate.prdType`）。
   - **期望值**：具体值或明确的匹配规则（等值、包含、正则、非空、集合成员）。
   - **值的来源**：这个值**来自哪里**——代码常量 / 入参回显 / DB 查询 / Redis / mock 报文 /
     配置中心 / 用户提供 / 外部真实接口。**必须写清楚**，写不出就是存疑点。
   - **是否随机**：同入参多次运行输出是否稳定。填"是"就只允许存在性 / 结构断言，
     下游 skill 会照此写用例。

   判断"是否漏字段"的口径：**如果这个字段错了或缺了，能不能证明命中了目标分支**。
   能证明的就必须列。模板 ID、券面值、路由目标、拼装出的 URL、消息 payload 里的关键 key
   都属于这类，不许省。

   **关于"值的来源"**：环境相关的业务常量（模板 ID、任务 ID、券值、可用 cid、库存 ID
   等）只存在于目标环境，不许从仓库 SQL、mock 平台历史值、PRD 示例值抄。
   拿不到就查环境或问用户，进存疑点。

把本批次的场景详情追加进 `02-scenarios.md`，同步把状态头的**批次进度**行更新为
「batch\<N\> 待确认」→ **暂停**，请用户确认本批次；确认后把这一批改成
「batch\<N\> 已确认」再展开下一批。全部批次都改成「已确认」后，`02-scenarios.md`
整体状态才能改成 `已确认`，进入阶段 3。

### 批次交付红线

每次只完整展开当前这一批的场景详情，其余未展开的批次在总览表里只占标题一行，
不写预期产出表。当前批次没有被用户确认之前，不写下一批的场景详情——即使觉得
"反正都想清楚了""场景不多一次写完更省事""这批和下一批关联紧密不如一起写"，
也不例外。**"用户想要一份完整的 02-scenarios.md"不等于"用户要一次看到所有批次的
预期产出细节"**——除非用户明确说"不分批"或明确要求把所有批次细节一次写完，
否则默认按批次逐一展开。

| 想法 | 现实 |
| --- | --- |
| 用户要"完整的 02-scenarios.md"，那就都写上 | "完整"指批次骨架已经定好、当前批次讲透了；所有批次细节一次吐给用户，等于没分批，看不过来的问题又回来了 |
| 场景不多，一口气写完更省事 | 场景数量不是分批的理由；哪怕只有几条，一次吐给用户还是会看漏、来不及纠偏 |
| 反正后面阶段 3-6 也按批次做，这里先把细节都定好省得来回 | 阶段 3-6 按批次做的前提是每批场景已经各自确认过、不会大改；批次没确认就把细节都写完，等于把"来回"浓缩成一次性大改的风险 |

出现以下任一情况，停下来只保留当前批次的产出：

- 已经在写下一批的预期产出表，但当前批次还没被用户确认；
- 因为"怕多轮来回麻烦"而想把没确认的批次也顺手写了；
- 用户没有明说"不分批"或"细节都写完"，只是笼统地要一份"完整"的 md。

## 收尾

两份 md 都要有存疑点章节。把存疑点逐个问用户，答案回填正文。
存疑点清空前不要把状态改成 `已确认`。
