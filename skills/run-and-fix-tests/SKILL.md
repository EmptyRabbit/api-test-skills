# 执行与修复

读 `05-case-design.md` 和用例代码，执行 pytest 并处理失败，产出 `06-run-report.md`。
产物结构见 [TEMPLATE.md](TEMPLATE.md)，红线见 `../generate-api-tests/CONVENTIONS.md`。

本 skill 可以单独调用：手改用例后重跑、或者过几天再回归一次。

## 流程

1. **检查环境**：python 环境是否可用、依赖是否装齐。
   **环境安装由用户人工处理**，本 skill 只检查并提示缺什么，不代为安装。
2. **确认前置**：把本批次 `05-case-design.md` 的执行前置清单摆给用户逐项确认——
   mock 配了吗、配置项改了吗、DB 连接填了吗、Pod 部署的是 feature 分支吗。
   没确认就跑，失败原因会全部混在一起，白白浪费一轮。
3. **执行** pytest，**只跑当前批次的用例文件**。
4. **读日志**：每条失败用例先打开 `logs/<用例函数名>.md`，看真实请求头、请求报文、
   响应报文。**不允许只凭 pytest 的 assert 摘要下结论**——摘要只有一个字段的差异，
   看不出是 mock 没生效、还是入参构造错了、还是被测逻辑真的不对。
5. **失败归因**（见下），按类型分别处理。
6. **重跑**，最多 3 轮。到上限仍失败就原样报告，不再自动改。
7. **产出报告**，落到 `docs/batch<N>/06-run-report.md`。

## 失败归因四分类

先定性再动手。分不清属于哪类时，先把证据摆出来问用户，不要瞎改。

| 类型 | 典型表现 | 处理方式 |
|---|---|---|
| 用例代码问题 | 字段路径写错、请求少字段、断言值笔误、fixture 没生效 | 直接改，重跑 |
| 测试数据问题 | mock 没生效、造的数据不对、配置项值不对、缓存没清 | 回到 `prepare-mock-data` 或 `prepare-framework-data` 修方案，或告知用户人工处理 |
| 环境问题 | 连不上 Pod、IP 变了、依赖缺失、库无权限、部署的不是 feature 分支 | 停下告知用户，不自行尝试绕过 |
| **疑似被测代码缺陷** | 响应与预期不符，且核对代码后逻辑确实如此 | **停下报告证据，严禁放宽断言** |

判断"mock 没生效"的方法：确认请求头带了 mock header（例：X-Mock-Id，具体由 vendor 适配定）、CaseId 与场景对应、
平台上该 Case 确实配了这个接口。三者都对还不生效，转为环境问题问用户。

日志是归因的第一手证据，四类失败在日志里的表现各不相同：

| 日志表现 | 指向 |
|---|---|
| 请求头没有 mock header（例：X-Mock-Id，具体由 vendor 适配定），或 CaseId 与场景不符 | 用例代码问题 |
| 请求头对、报文对，但响应里的下游数据不是 mock 的值 | 测试数据问题（mock 未生效） |
| 没有日志文件，或 HTTP 状态码 4xx / 5xx | 环境问题 |
| 请求报文完全符合场景，响应也是业务码，但与预期不符 | 对代码后可能是疑似缺陷 |

## 红线：不许改用例迁就 bug

发现疑似缺陷时，报告必须包含四样东西：

- 完整请求报文——直接引用 `logs/<用例函数名>.md` 的路径，不要手工粘片段；
- 实际响应——同上；
- 预期结果；
- 判断依据（代码文件行号，或 PRD 的哪一条）。

**绝不允许**把断言改成实际返回值、放宽成多值可选、或者给用例加 skip 让它变绿。
发现 bug 是这套流程存在的意义，把 bug 掩盖掉等于前面所有工作白做。

## 报告

`06-run-report.md` 记录：每轮执行结果、失败归因、修复动作、遗留未通过用例、
疑似 bug 清单。

**收尾汇报按下面这个口吻**——先给结论、再讲要用户做的事，控制在几句话：

> batch1 跑完，7/8 通过。剩下 `test_paid_order_notified` 是疑似 bug（PAID 订单没触发通知，
> `OrderNotifyProcessor.java:142` 提前 return 了），要开发看一下。其他用例都稳，
> 你确认没问题就可以起 batch2。

反例（不要这样写）：

> 本次执行共 8 条用例，其中 6 条通过，2 条失败，经归因分析，1 条为用例代码问题已修复，
> 1 条为疑似被测代码缺陷，详见报告第四节，请查阅确认。
