# 框架数据准备

读 `01-change-analysis.md` 的依赖清单、当前批次的 `02-scenarios.md`、以及 `03-mock-plan.md` 末尾的
「遗留数据需求」，产出 `04-framework-data.md`。

这份 md **与测试框架无关**。它只写清每个场景要做什么数据动作。
`api-write-pytest-cases` 把其中「执行方=自动」的动作渲染成 pytest fixture；
端到端测试把同一批动作插进 UI 步骤。本阶段不写 fixture，也不写某个客户端的调用代码。

## 批次范围

只处理**当前批次**的场景。直接读 `docs/batch<N>/02-scenarios.md`，里面的场景全部
属于本批，不用再筛。其他批次的场景文件一律不碰。

产物落到 `docs/batch<N>/04-framework-data.md`，状态头的阶段写成 `batch<N>/04-框架数据`。

工具用法见 [TOOLS.md](TOOLS.md)，产物结构见 [TEMPLATE.md](TEMPLATE.md)，
红线见 `../api-generate-api-tests/CONVENTIONS.md`。

## 关于工具

本 skill 只讲**通用方法论**：现状核查、造数动作、清理、人工待办。
**具体查询工具**（数据库查询 MCP、配置中心查询 MCP）由 vendor 适配 skill 提供。

vendor 适配（`api-prepare-framework-data-<vendor>`）只补充查询工具和平台事实
（网关地址、集群名从哪来、缺了哪个参数要标在动作上）。适配 skill 同样不往这份 md 里写客户端调用代码。

## 产物是什么

`04-framework-data.md` 按这个顺序写：

1. 状态头 + 一句话结论
2. 按场景的数据需求总表
3. 每类依赖一节：先现状核查，再一张造数动作表
4. 人工待办清单
5. 存疑点

造数动作表的列固定为：场景、目标、操作、数据、清理、执行方。

| 列 | 写什么 |
|---|---|
| 目标 | 库和表、集群和 key、配置文件和 key，或消息 subject |
| 操作 + 数据 | 可照做的动作。DB 写 SQL 和参数；Redis 写 key、value、TTL；消息写 subject 和 payload 字段 |
| 清理 | 动态造出来的数据怎么删。环境里本来就有的写「不动」 |
| 执行方 | 只有两档：`自动`（下游照表执行）、`人工`（同时抄进人工待办） |

操作和数据用文字或 SQL 写完。下游消费方再把「自动」行渲染成自己的步骤。

## 统一逻辑

每类依赖都走同样三步：**先查清现状 → 再定造数动作 → 标清清理和执行方**。

先查现状这一步不能省。不查就造，很容易撞主键、覆盖别人的数据、或者造了一堆
其实环境里本来就有的东西。

## 四类依赖

### DB

- 库名表名优先从代码分析（mapper / XML / DAO），其次用数据库查询工具查，都不行问用户；
- 查表结构和现有数据，确认每个场景需要哪几行、字段值分别是什么；
- 动作表写 INSERT / UPDATE 的 SQL、参数、对应的清理 SQL；执行方为 `自动`；
- 造数前先查一次，避免主键 / 唯一键冲突；已存在且能复用的数据，清理写「不动」；
- 连接信息（host / port / 账号 / 密码）拿不到就列进人工待办，让用户填 `config.yaml`。

### Redis

- 集群名从代码配置或注入点分析，拿不准问用户；
- 动作表写清 key、value、TTL，以及清理时删除哪个 key；执行方为 `自动`；
- **常见坑**：接口有缓存时，造完 DB 数据要另加一条清对应缓存 key 的动作，否则测不到新逻辑。
  分析时主动检查这一点。

### 配置中心

- 用配置中心查询工具**只读**查出每个 key 的当前值（工具名由 vendor 适配指定）；
- 执行方默认 `人工`：待办表写 key / 当前值 / 本次需改成 / 测完还原为；
- 需要 agent 代改时必须先征得用户同意，并把原值记进 md 防止忘记还原；
- 受影响的场景在动作行注明「执行前需确认配置项 X = Y」。

### 消息中间件（MQ）

- 场景要靠消息驱动时，动作表写 subject、payload 字段、方向=发送、执行方=`自动`；
- 接口副作用是发消息时，另起一行方向=拉取验证（这是断言，不是造数），清理写「无」；
- 网关地址、缺的参数（如 appid）由 vendor 适配写进行或人工待办，不写客户端调用。

## 收尾

md 里必须有一份**人工待办清单**，汇总用户要亲自做的事：填 DB 连接信息、
手动改配置中心、以及所有 agent 拿不到的信息。接口测试由 `api-write-pytest-cases`
把这份清单合并进执行前置清单；端到端测试把它合并进 UI 用例的前置步骤。
