# 通用约定

本文件是这套接口测试 skills 的共享约定，所有子 skill 都遵守。

## 红线（不可违反）

1. **不确定就问用户**。推断不出的信息一律停下来提问，禁止猜测后继续。
2. **文档与代码冲突必须显式确认**。PRD、用户描述与代码实现不一致时，把差异点单独列出来问用户
   以哪边为准——可能是文档过时，也可能是代码 bug，结论直接改变预期结果。
3. **预期结果校验到位**。响应做字段级完整断言，有副作用时补 DB / Redis / 消息中间件落地断言。
4. **场景预期必须穷举到关键字段**。每个场景在阶段 2 就要列出调用链每一步的关键产出字段、
   期望值、值的来源、是否随机；缺一列就是没做到位。
5. **禁止防御性模糊断言**。不写 `assert x is True or str(x).lower() == "true"`、
   不写大小写兼容的字段查找。字段结构必须在分析阶段确定；确定不了就当存疑点问用户。
   标记为"随机"的字段只允许存在性 / 结构断言，不许锁死具体值。
6. **禁止改用例迁就被测代码缺陷**。怀疑是 bug 时停下报告证据，绝不放宽断言让用例变绿。
7. **只读探查自由，写操作需授权**。调接口、查库、读配置、捞 trace 可自由进行；
   改配置项、写库、发消息前必须先获得用户同意。
8. **一律中文、一律 Markdown**。skill 输出、中间产物、用例注释、对话全部用中文，
   中间产物全部是 md 文件。
9. **vendor 专有用词（公司名、内部平台名、内部工具名）只允许出现在
   `-<vendor>` 后缀的适配 skill 里**。核心 skill 用通用术语（HTTP / RPC、
   配置中心、消息中间件、Redis 集群、APM、数据库查询 MCP 等）。

## 产物目录结构

产物目录由用户指定，例如 `myapp/tests/generated`：

```
<产物目录>/
├── docs/
│   ├── 00-context.md          输入信息与环境上下文（全量）
│   ├── 01-change-analysis.md  代码改动分析与依赖清单（全量）
│   ├── 02-scenarios.md        测试场景清单，含批次列（全量）
│   ├── batch1/                第 1 批：主流程
│   │   ├── 03-mock-plan.md
│   │   ├── 04-framework-data.md
│   │   ├── 05-case-design.md
│   │   └── 06-run-report.md
│   └── batch2/                第 2 批，结构同上
├── frame/                     复制自 write-pytest-cases/template
├── tests/                     生成的 pytest 用例，多文件
├── logs/                      每个用例的请求响应日志，不入 git
├── conftest.py
├── config.yaml
├── .gitignore
└── requirements.txt
```

## md 状态头

每份中间产物开头必须有状态头，主编排靠它判断进度：

```markdown
> 阶段：02-测试场景
> 状态：待确认
> 上游：01-change-analysis.md
> 更新时间：2026-08-25 15:30

**一句话结论**：本次改动集中在 `XxxProcessor` 的空城市兜底分支，围绕它设了 6 条场景，
其中 batch1 冒烟 1 条，剩余 5 条边界与回归塞在 batch2。存疑点还剩 1 条待用户裁决。
```

状态头下面**必须**紧跟一行加粗的「一句话结论」——写这份 md 得出了什么、还欠什么。
用户 review 时先看这句，再决定要不要读全文。写不出这句结论就等于阶段没做完，
不要用"本方案完成了 XX、YY、ZZ"这种复述章节的写法糊过去。

批次目录里的 md，状态头的「阶段」要带批次号，例如 `> 阶段：batch1/03-mock 方案`。
主编排靠这个判断哪一批走到哪一步。

- `状态` 取值 `待确认` / `已确认`；
- 用户 review 通过后才改成 `已确认`，下一阶段才允许启动；
- 用户可以直接编辑 md 内容（删场景、改报文、补字段），编辑等同于下达指令，
  继续时以 md 里的最新内容为准。

## 输出口吻

写给一起做项目的同事看，不是给用户交报告。

- 有判断就写判断，不要只堆事实。"queryUserCoin 建议 mock，因为需要空返回，FAT 库里都是有券用户，
  临时清号不划算" 比 "构造成本高，建议 mock" 强得多。
- 少用"综上所述""本方案""如上表所示"这类连接语。段落之间靠内容自然衔接，不要人为造过渡。
- 不确定的地方直接说不确定，别包装成"待进一步确认"。
- 表格里的说明列该写一句话就写一句话，不要一句话拆两行凑排版。

## 存疑点章节

每份中间产物末尾放一个「存疑点」章节，列出推不出来的问题。这些问题要当面逐个问用户，
拿到答案后回填进正文，并从存疑点里划掉。存疑点没清空前，状态不得改为 `已确认`。

## 可用的只读探查工具

能力层面（具体工具由 vendor 适配 skill 指定）：

| 能力 | 用途 |
|---|---|
| APM / trace 探查 | 捞真实请求 / 响应报文，确认接口结构 |
| 数据库查询 MCP | 执行 SQL 或查文档库，确认表结构与现有数据 |
| 配置中心查询 MCP | 读取配置当前值、查变更历史 |
| 技术文档检索工具 | 语义检索内部文档，了解不熟悉的框架工具 |
| PRD 文档读取工具 | 读取需求文档 |
